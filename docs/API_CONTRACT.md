# Parallel implementation contract

All domain functions mutate an AppState inside a store transaction and throw DomainError (status/message). Export `handleReviewCommand(state, actor, command): unknown` and `handleWorkflowCommand(state, actor, command): unknown`. Return null for unrecognized commands. Command shape is type plus validated fields; shared helpers in server/domain.ts. Root applies idempotency and store transaction around every command. Shared types in lib/types.ts. Use these names; communicate any additions.

Review commands: `createPackage {title,period,entity,dueAt}`, `addVersion {packageId,fileId,producedAt,sections,expectedRevision}`, `updateVersion {versionId,sections,expectedRevision}`, `publishVersion {versionId,expectedRevision}`, `saveResponse {assignmentId,metricId,answer,comment,expectedRevision}`, `submitReview {assignmentId,expectedRevision}`, `signReview {assignmentId,expectedRevision}`, `reopenReview {assignmentId,reason,expectedRevision}`, `finalizePackage {packageId,expectedRevision}`, `addComment {assignmentId,body,metricId?}`. The fileId references a validated Evidence record. addVersion creates draft only. Missing evidence rejects. All current-version checks server-side.

Workflow commands: `saveTemplate {templateId?,name,nodes,edges,expectedRevision?}`, `publishTemplate {templateId,expectedRevision}`, `createRun {templateId,period,name?}`, `taskAction {runId,taskId,action:'start'|'submit'|'attest'|'reopen'|'forecast'|'rebind',expectedRevision,reason?,forecastAt?,documentVersionId?}`, `attachEvidence {runId,taskId,evidenceId,expectedRevision}`. Handle pattern reuse via saveTemplate copies/sourceTemplateId if feasible. Export `getTaskImpact(state,runId,taskId)` and `taskBlocked(state,run,task)` for computed UI/read API. Root invokes workflow gate invalidation after document publish/reopen as needed; expose `invalidateDocumentGates(state, actor, packageId, reason)`.

Platform exports: store.ts `readState():Promise<AppState>`, `transact<T>(fn:(state:AppState)=>T|Promise<T>):Promise<T>`; auth.ts `getPrincipal(request:Request):Promise<Principal>`, `isLocalMode():boolean`; files.ts `saveFile(bytes:Uint8Array,filename:string,actor:Principal,entity:string):Promise<Evidence>` and `readFile(evidence:Evidence):Promise<Uint8Array>`; databricks.ts `fetchDatabricksData(actor,entity):Promise<unknown>`; notifications.ts worker entry separately. Store creates empty state in prod; seedState in local mode only. Auth may use readState for approved users.

Browser API: GET /api/state returns AppSnapshot with scoped records plus principal/localMode; POST /api/commands accepts command including optional idempotencyKey (required for sign/attest via root); POST /api/files multipart file+entity returns Evidence; GET /api/files/:id serves authorized original PDF; GET /api/export?packageId=... returns manifest; GET /api/impact?runId=...&taskId=...; GET /api/databricks?entity=... . All mutations JSON response {result}; errors {error}. Client reloads snapshot on success. Development principal via x-workeva-user header (only explicit local mode); production must verify Entra credentials. Root will provide src/lib/client.ts for client request helper.

## Review operations

Signing and attestation commands use the idempotency cache. Other commands rely on their expected revision and do not replay cached mutations. Every API write reloads the active principal inside the transaction so access changes take effect before authorization.

- Issues: `createIssue {assignmentId,ownerId?,category,title,description,metricId?}`, `commentIssue {issueId,body,expectedRevision}`, `proposeIssueResolution {issueId,explanation,expectedRevision}`, `acceptIssueResolution {issueId,expectedRevision}`, `reopenIssue {issueId,reason,expectedRevision}`. Only the assigned reviewer accepts a proposed resolution. Unresolved issues block signing and finalization; replacement publication carries them into the corresponding section or rejects an orphaned issue.
- Administration: `saveAssignmentRule {rule,expectedRevision?}`, `upsertUser {id,name,email,roles,entities,active,expectedRevision?}`, `reassignReview {assignmentId,newReviewerId,reason,expectedRevision}`. Updates to existing users/rules require their current revision. Rules contain entity, optional sectionId, primaryReviewerId, backupReviewerIds, additionalRequiredReviewerIds, effectiveFrom and optional effectiveTo, using inclusive YYYY-MM-DD dates. Production user IDs must match Entra object IDs.
- Notifications: `markNotificationRead {eventId}`, `saveNotificationPreferences {preference,expectedRevision?}`, `nudgeReview {assignmentId,message?}`, `nudgeTask {runId,taskId,message?}`. Preferences belong to the authenticated user and include emailEnabled, reminderIntervalMinutes, timezone, quietHours `{start,end}` in HH:mm, and urgentBypassQuietHours. Existing preference updates require the current revision. Manual reminders require scoped management access and are rate limited.

Read links: `/reviews?assignmentId=…`, `/tasks?taskId=…`, `/issues?issueId=…`. The scoped snapshot includes issues, assignment rules/history and the current user's notification preferences/receipts. These collections are optional in older stored aggregates.
